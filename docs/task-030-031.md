# TASK-030 / TASK-031

Requires Node.js 22+, `npm ci`, the existing `places` schema and
`sync_places_universe_batch` RPC from the catalog setup. Python jobs remain compatible.
The API names `contentid`, `contenttypeid`, `firstimage`, `areacode`, `sigungucode`
map to existing DB columns `content_id`, `content_type_id`, `first_image`,
`area_code`, `sigungu_code`. No duplicate identity columns are introduced.

## Installation

Apply `supabase/migrations/20261028074529_batch_tour_enrichment.sql` to the same
project specified by your server environment file. It adds the status/JSONB columns,
course tables, leases, a private quota ledger and service-role-only RPCs. Existing
`overview` values are preserved during migration. New course tables have RLS and
visitor read policies restricted to active parent places. The parent places key is
`content_id`; the requested course key remains `tour_courses.contentid`.

Use a server-only `.env` or pass `--env-file PATH`. Required variables:
`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `TOUR_API_DECODING_KEY`.
`NEXT_PUBLIC_SUPABASE_URL` is accepted as the URL fallback; a public/anon key is
never accepted as the server key. No populated environment file belongs in Git.
Both CLIs check the new migration before consuming TourAPI quota.

## TASK-030: one-off nationwide catalog

```sh
npm run sync:master -- --env-file /path/to/server.env
```

This is a one-off command; it installs no schedule. It walks all eight types
12/14/15/25/28/32/38/39, requests 1000 items/page and writes at most 100 rows/RPC.
The existing RPC performs `ON CONFLICT (content_id) DO UPDATE`, compares source
revision and preserves stored/enriched images. Course 25 uses exactly the same
places mapping and write path. Invalid/nonfinite/zero/out-of-Korea coordinates
(longitude 124..132, latitude 33..39) are excluded and counted/logged. No guessed
coordinates are inserted. Text fields respect the actual title/address limits.
Missing identity, corrupt modified timestamps and rejected data records are logged
with ID/category/code only. A rejected transaction is split to isolate bad records.
Transport/auth/schema outages stop with an error instead of dropping the catalog.
Repeated records, empty/incomplete pages and changing totals fail visibly; rerun
is idempotent. Full catalog runs never advance the existing incremental checkpoint
and never deactivate places absent from a full scan.

## TASK-031: batch-tour-enrichment

```sh
npm run batch-tour-enrichment -- --env-file /path/to/server.env
# Bounded verification; retry failed records on a subsequent run:
npm run batch-tour-enrichment -- --env-file /path/to/server.env --limit 20
npm run batch-tour-enrichment -- --env-file /path/to/server.env --retry-failed
```

`p-limit(10)` limits actual HTTP requests across common, intro, course pages and
retries. A separate ten-place worker pool keeps memory bounded. Claims are acquired
in batches of at most 100 using `FOR UPDATE SKIP LOCKED`; concurrent workers cannot
own the same place. NULL is unprocessed, pending is leased, completed is committed,
failed is an individual bad response. A stopped/crashed worker's 30-minute lease
can be reclaimed. Daily exhaustion and a runtime boundary release unstarted work
back to NULL. Failed records are included only with `--retry-failed`, at most once
per invocation. Changes to source modified_time/category invalidate completion and
old tokens; a stale worker cannot overwrite a newer source revision.

Every place requires `detailCommon2` and `detailIntro2`; overview and sanitized intro
JSON are persisted together. Event dates must be valid YYYYMMDD calendar dates or
are stored as null. A course additionally loads every `detailInfo2` page, validates
stop order/identity, sorts source subnum and stores a contiguous one-based order.
The course and its replacement stop list are committed in the same transaction as
place completion. Incomplete/duplicate stops never produce a completed course.
Individual payload errors mark failed and processing continues. Database/schema/
auth errors stop the run and retain retryable work.

## Quota, runtime and reports

Both new commands share a DB ledger scoped to SHA-256 of the decoded service key
and the KST day. Reservation is atomic, persists before every HTTP attempt and
includes retries. Provider quota code 22 blocks the rest of that day. A local
persistent journal adds conservative accounting and prevents two local CLIs from
running with the same key. Reservations are intentionally not refunded after a
transport error or crash. The limit can be lowered with `--daily-limit N` but
cannot exceed 100000. `--already-used N` seeds already consumed calls for the
current KST day; it is not reapplied after midnight.

Old Python pipelines, other repositories and external consumers do not use this
new ledger. Stop those runs before a full backfill or seed their current-day usage
with `--already-used`. Do not delete runtime journals to regain quota. Local dead
process locks are recoverable; locks from another host require operator review.

The default enrichment limit is 500000 places and the default runtime is 7200
seconds. `--limit N` and `--max-seconds N` bound enrichment only; catalog always
performs a complete walk. The runtime boundary prevents new place work, while
in-flight requests drain with timeouts and bounded retry backoff.

JSON reports include fetched/claimed/completed/skipped/failed counts, API attempts,
elapsed time and measured requests/second. Exit codes: 0 finished the selected
work, 1 failed, 2 quota/runtime deferred (resume later). Logs never include API URLs,
keys, raw response bodies or Supabase error messages.

Concurrency 10 is a cap, not a throughput guarantee. 38000 places require at least
76000 calls plus course pages and retries; 20 calls/second requires at least about
63 minutes. A 35-minute run needs over 36 calls/second before DB/network overhead.
The actual baseline DB contains more than 38000 places, so remaining daily work
may be deferred rather than exceeding quota. No live throughput target is claimed
without a measured production run.

## Verification

```sh
npm run typecheck
npm test
python -m unittest
```

Node tests cover full 1000-row paging, course 25 mapping, payload sanitization,
request concurrency, persistent KST quotas/retries and per-place failure isolation.
An embedded PostgreSQL test executes the migration, repeats it, and checks claims,
atomic course rollback, stale tokens, source invalidation, failed retries, quota
limits and visitor RLS. CI runs both Node and the existing Python suite. Production
migration application and live backfills are separate from these offline checks.
